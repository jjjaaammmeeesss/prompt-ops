# v2.3 Co-evolution 根因报告

## 一、问题总览

**一句话总结**：v2.3 启动了一轮"prompt 自我进化"，但诊断偏差（diagnostic bias）来自 prompt 框架层的结构性倾斜，Mutator 唯一的工具箱"加规则"只能在上层打补丁，最终造成 M1 崩溃（触发准确率 -28%）、对抗用例生成失效、DECIDE 逻辑 bug 三重叠加，3 轮迭代后综合分从 0.686 退化到 0.646（-5.8%），无一轮真正超越基线。

| 轮次 | 提示词 | n_runs | 综合分 overall | M1（触发准确率） | M5（tone 匹配） | 判定 |
|------|--------|--------|---------------|-----------------|-----------------|------|
| R0 | v2.3 | 1 | **0.686** | 69.4% | ~0.400 | baseline |
| R1 | v2.4 | 3 + denoise | 0.666 | 50.7% | 0.343 | DISCARD |
| R2 | v2.4 | 1 (单次验证) | 0.684 | ~70.8% | — | KEEP（DECIDE bug：比较对象已退化） |
| R3 | v2.5 | 3 + denoise | 0.646 | 51.6% | 0.357 | DISCARD |

---

## 二、五个根因

### 根因一：Prompt 框架层的结构性 diagnostic bias（严重程度：高）

**现象**：v2.3 在 gold=empowering 占 84% 的盲区案例池中，M5 仅 0.400——系统在 60% 的应鼓励案例中输出了诊断语气。v2.3→v2.4→v2.5 三轮迭代，M5 始终在 0.34-0.40 区间，从未突破。

**机制**：bias 不是某一条规则写错了，而是三个结构特征锁死的：

1. **角色隐喻定义了诊断默认值**。"帮家长从收紧的框里松一松"——隐喻框架把家长定位为"有问题需要被松一松"的对象，鼓励是条件从句的后半句（"如果他已经在努力"），成为例外情形。
2. **诊断的动词网络远比鼓励丰富**。诊断方向有"看见→松一松→发现→指出→接住→理解"的完整认知动作链；鼓励方向只有"轻轻说→点出"。LLM 在处理时，诊断路径有更密集的语义锚点。
3. **内部推理三步（情绪层→动机层→决策层）是天然的分析框架**。整套流程产出"我发现了什么盲区"而非"我欣赏了什么"。等模型读完三步做完分析，再读到"先找对的，有则鼓励"时，诊断方向已经触发，决策规则只能事后纠偏。

**为什么"加规则"无效**：Mutator 在 prompt 末端加"先找对的→有则鼓励→无则诊断"的决策规则，但这是个认知层指令，而前三节的"观察→分析→指出"是行为层框架。LLM 先执行行为框架，诊断已经完成了，规则补丁打在了错误的位置。

---

### 根因二：M1 崩溃——空输出导致的伪退化（严重程度：高）

**现象**：R0 (v2.3, n=1) M1=69.4%，R1 (v2.4, n=1) M1=69.4%——同一份 v2.4 提示词，单次运行与 v2.3 一字不差。但 R2 (v2.4, n=3 + denoise) M1 骤降到 50.0%。28 个 case 在 3 次运行中多数输出空 popup_text。

**机制**：这不是提示词退化，是测量体系切换暴露了模型固有的非确定性。

```
模型非确定性 (temperature=0.3)
  → 对 borderline case 有 ~20-40% 概率输出空 popup
    → n=1 评估：碰运气，40% borderline case 至少有一次通过
    → n=3 + 多数投票：2/3 空输出 → M1=0，case 被判死
      → M1 从 69.4% 表观骤降到 50.0%
```

关键证据：R1 和 R2 用的是**同一份 v2.4 提示词**，唯一区别是 n_runs 从 1 变成 3。不是提示词变长导致格式崩溃（R1 同样长度的 prompt 无此问题），不是 API 失败（R2/R3 共 66 个 M1=0 case，零 error 字段）。模型的失败模式是输出合法 JSON 但 popup_text 为空字符串——即"选择不输出内容"。

**空输出的深层原因**：v2.4 新增的"先问自己→有则鼓励无则诊断"顺序门增加了认知负担。模型在 borderline case 上陷入决策冲突（"我没有找到足够明显的'对的'，但也不确定该诊断什么"），选择沉默。

---

### 根因三：DECIDE 逻辑 bug——"跟上一轮比"而非"跟原点比"（严重程度：中）

**现象**：R2 的 v2.4 得分 0.684（n=1 单次验证跑），比 R1 的 v2.4 得分 0.666 高 0.018，被 KEEP。但 0.684 < 0.686（v2.3 原点），v2.4 实际比基线差。

**机制**：`should_keep()` 的语义本是"候选版 vs 原点基线"，但三个调用方（`optimizer.py`、`v23_evolve.py`、`run_auto_evolve.py`）都将 `baseline` 变量在 KEEP 后重赋值为上一轮 candidate，实际执行的是"候选版 vs 上一轮最佳"。修正后的逐轮判定：

| 轮次 | candidate | 分数 | vs v2.3 (0.686) | Δ | 修正判定 | 原判定 |
|------|-----------|------|---------------------|------|---------|--------|
| R1 | v2.4 | 0.666 | 0.686 | -0.020 | DISCARD | DISCARD |
| R2 | v2.4 | 0.684 | 0.686 | -0.002 | DISCARD (未达 MIN_OVERALL_IMPROVEMENT=0.003) | **KEEP** |
| R3 | v2.5 | 0.646 | 0.686 | -0.040 | DISCARD | DISCARD |

如果用 R2 的 n=3 分数 0.627，差距更大（-0.059），同样 DISCARD。修正后**所有轮次都 DISCARD，无退化版本被错误保留**。

**额外问题**：`MIN_OVERALL_IMPROVEMENT = 0.003` 没有与 judge 噪声量级校准。v2.4 在 n=1 中得 0.684，在 n=3 中得 0.627——同一 prompt 的评估噪声幅度高达 **0.057**。0.003 的阈值在噪声面前没有区分力。M1 也不参与 `overall_score` 的计算，导致 -28% 的 M1 崩溃对 `should_keep` 完全不可见。

---

### 根因四：对抗用例生成失效——预验证逻辑缺陷 + 同质化（严重程度：中）

**现象**：3 轮 9 次生成尝试，两个 mode 几乎零有效产出。`tone_blindspot_diagnostic_bias` 全部 0 通过（LLM 无法生成可解析 JSON），`tone_blindspot_empowering_bias` 仅 1 个案例通过预验证（且通过 M6_low 路径而非 tone 路径）。最终 8 个产出中 7 个是同质化的 empowering case，与 62 个 golden case 中的 50 个 empowering case 高度重叠。

**机制**：

1. **`tone_blindspot_diagnostic_bias` 的定义与 v2.3 的全局行为无法区分**。该 mode 描述"系统应在鼓励时错误输出 diagnostic"，但 v2.3 下所有 empowering 案例都会触发 diagnostic bias。LLM 被要求生成"能特殊触发此 bias 的案例"，但无法区分"特殊案例"和"普通案例"，输出结构松散、JSON 解析失败。

2. **`tone_blindspot_empowering_bias` 的预验证逻辑与 v2.3 反向**。该 mode 预期 sys_tone=empowering 才算触发失败，但 v2.3 的 dominant bias 是 diagnostic——系统几乎从不输出 empowering。对所有 `expected_tone=diagnostic` 的案例，sys_tone=diagnostic → M5=1.0 匹配 → tone 检查不触发失败 → 案例被丢弃。

3. **产出的 8 个案例高度同质化**。7 个共享"孩子帮忙→造成损失→家长失望→孩子退缩"模板，三个案例仅变量替换（洗坏衣服/浇死多肉/打碎鸡蛋）。唯一的例外来自 empowering_bias mode 但通过 M6_low 路径进入——它实际测试的是另一个失败模式。

**后果**：对抗案例只占总池 ~11%，在 `should_keep` 决策中几乎无区分力，所有决策均由 M1 崩溃驱动。

---

### 根因五：Mutator 策略空间单维——只有"加规则"一个动作（严重程度：中）

**现象**：3 轮迭代，每轮变异方向完全一致——回应对 tone bias 的失败分析，添加更多"先鼓励"的决策规则。净效果是 prompt 更长、约束更密、决策树更复杂，但综合分持续下降。

**机制**：这不是参数调得不对，而是策略空间本身是单维的。

1. **FailureReport 做了正确的统计但给了错误的归因**。42/45 个失败案例标签是 "expected empowering, got diagnostic"，Mutator 看到的永远是同一个模式，它唯一的工具箱就是"加更多鼓励规则"。FailureReport 缺少关键的元分析层：判断当前失败模式是由"规则缺失"还是"框架矛盾"造成的。

2. **"加规则"只在特定场景有效**：遗漏具体可枚举边界条件、已有正确框架需微调、规则是正面范例而非禁令。本案三个条件都不满足——根因是 prompt 架构的结构性偏向、新规则与旧框架存在隐式矛盾（"先找问题" vs "先找对的"）、prompt 已足够长导致模型对后段指令依从度下降、规则间优先级模糊（安全底线 vs 善意推定 vs 鼓励优先冲突时谁先）。

3. **M1 崩溃是"加规则"策略失效的最强信号**。新增规则在模型内部制造了不可调和的张力——模型在有矛盾的约束中选择沉默。28 个 case 完全无输出。

## 三、根因优先级排序

按修复后预期收益从高到低：

| 优先级 | 根因 | 修复方向 | 预期收益 |
|--------|------|---------|---------|
| **P0** | 根因一：结构性 diagnostic bias | 删减架构元素（删除 `contradiction` 输出字段、删除"诊断式/鼓励式"显式分类）；重排架构顺序（价值观→内心操作→精简框架→格式） | 如果 M5 从 0.40 提升到 0.60+，overall 可从 0.686 推至 0.73+ |
| **P1** | 根因二：M1 空输出崩溃 | 空输出视为"未完成"触发重试；降噪逻辑对 M1 用宽松策略（至少 1 次有效输出即采纳）；删除 v2.4 的"先问自己"顺序门，恢复并行对称结构 | 恢复 M1 从 50% 到 69%+，直接贡献 overall 提升 ~0.02-0.04 |
| **P2** | 根因三：DECIDE 逻辑 bug | 锁定 `baseline_round_000.json` 为唯一比较基准；将 M1 纳入 `overall_score`；阈值基于 bootstrap SE 校准 | 防止退化版本被错误 KEEP，修正后 3 轮全部 DISCARD，阻止 0.038 的净退化 |
| **P3** | 根因五：Mutator 策略空间单维 | 重构为多策略探索框架（删减/重排/范例/温度四个策略族并行探索） | 使后续迭代的变异多样性从 1 维扩展到 4 维，避免重复"加规则→崩 M1"的死循环 |
| **P4** | 根因四：对抗用例生成失效 | 修复预验证过滤器的 mode-aware 逻辑；为 tone_blindspot 模式提供具体案例锚点替代泛化描述 | 提升对抗用例池的区分度和覆盖率，使 `should_keep` 不再仅由 M1 驱动 |

## 四、修复依赖关系

```
P0（结构性 diagnostic bias）
  ├── 是 P1（M1 崩溃）的前提：删除 contradiction 字段和显式 tone 分类
  │   可直接降低模型的认知负担，减少决策瘫痪 → M1 自然恢复
  │
  ├── 是 P5（对抗用例失效）的间接前提：tone bias 方向反转后，
  │   empowering_bias mode 的预验证逻辑才能正常工作
  │
  └── 不依赖其他根因的修复，可独立先行

P1（M1 崩溃）依赖 P0 的架构删减，但在评估管道侧的修复
  （空输出重试、降噪宽松策略）可以立即独立执行，不等 prompt 改动

P2（DECIDE bug）完全独立，可与 P0/P1 并行修复

P3（Mutator 重构）依赖 P0 完成——只有当 prompt 的"正确形态"
  （删减而非添加）被确认后，Mutator 的策略空间才有意义

P4（对抗用例生成）依赖 P0 完成——tone bias 方向反转后，
  tone_blindspot_empowering_bias 的预验证逻辑自动修正
```

**建议的执行顺序**：P2（纯代码修复，无风险）→ P0（prompt 架构重构）→ P1（在 P0 基础上验证 M1 恢复 + 评估管道修复）→ P3（Mutator 重构）→ P4（对抗用例生成修复）。

**关键约束**：P0 和 P1 的 prompt 侧修复必须在同一轮迭代中一起落地。如果只修 P0 不改评估管道，新 prompt 的 M1 可能仍被噪声淹没；如果只修评估管道不改 prompt，M5 的 diagnostic bias 不会改善。两者解耦会导致误判。
