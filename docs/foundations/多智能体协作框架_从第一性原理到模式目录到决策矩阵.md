## 问题起源

**问题一**：偏向于生产端的多智能体协作，尤其是多智能体对话式协作（"老板在群里 @ 员工"），为何不是主流框架？这种形式看起来是最直观、最容易理解的。

**问题二**：什么是基于 AI 时代的多智能体最佳协作框架？从第一性原理进行深度思考和推导。

**回答路径**：从第一性原理出发，穷举所有理论上可行的协作拓扑结构，打破"DAG 唯一论"的预设，建立完整的五维原语空间 → 模式目录 → 决策矩阵。

## L0 · 第一性原理

从最底层的约束开始推导：

| # | 原理 | 含义 |
|---|------|------|
| P1 | **专业化分工** | 不同 agent 有不同的能力边界（工具、知识、推理风格）。协作框架必须让每个 agent 做它最擅长的事。 |
| P2 | **信息最小化** | 每个 agent 只应接收完成当前任务**必需**的信息。多余信息 = 噪声 + 成本。 |
| P3 | **最大化并行** | 无依赖的任务应并发执行。串行化一切是对算力的浪费。 |
| P4 | **接口类型化** | Agent 之间的信息传递必须结构化、可验证。自然语言作为接口 = 把编译器换成了传话游戏。 |
| P5 | **故障隔离** | 一个 agent 的失败不应级联。框架必须能检测、重试、或优雅降级。 |
| P6 | **可观测性** | 每一步的输入、输出、耗时、token 消耗必须可追踪。黑盒多 agent 系统 = 不可维护。 |
| P7 | **人在关键决策点** | 人不应微操每一步，但应在**不可逆行动**和**高不确定性分支**上做决策。 |

### 群聊为何违反第一性原理

| 原理 | 群聊的表现 |
|------|-----------|
| P2 信息最小化 | 全员看到所有消息，上下文窗口爆炸（O(n²) token） |
| P3 最大化并行 | 聊天天然串行——你一句我一句，即使任务独立也要排队 |
| P4 接口类型化 | 状态隐藏在自然语言中，agent 要从聊天记录里"找"信息 |
| P5 故障隔离 | 一个 agent 跑题会带偏全场，无法独立回滚 |
| P6 可观测性 | 调试靠翻聊天记录，无结构化 trace |

**群聊的甜区**：探索性任务——还不确定怎么做、需要多视角碰撞、人类需要实时介入。它的灵活性在探索阶段是优势。

## 微观层 · 单Agent执行循环（Loop）

> **来源**：提炼自 loop-library skill 的核心设计理念——loop 是一个带终端状态的反馈系统，不是无限自主的许可证。

如果说 L1-L2 的五维原语和 20 个模式描述的是**多个 agent 之间怎么协作**（宏观分子层），那么 Loop 描述的是**一个 agent 内部怎么执行**（微观原子层）。一个 Loop 就是协作拓扑图中的一个节点。

### 六步心跳：单个 Agent 的执行周期

```
         ┌─────────────────────────────────────┐
         │           反馈（循环的核心）           │
         │   ┌──────────────────────────┐      │
         │   │                          │      │
         ▼   │                          │      │
   ┌─────────┴──┐  ┌──────┐  ┌──────┐  ┌──────┴┐  ┌────────┐
   │ 1.Observe  │→│2.Choose│→│ 3.Act │→│4.Verify│→│5.Record│
   │ 读最新状态  │  │选最高  │  │做一个 │  │用可观测 │  │保存动作 │
   │ 收集证据    │  │价值动作│  │有界   │  │标准验证 │  │证据结果 │
   │            │  │       │  │可逆改 │  │        │  │剩余工作 │
   └────────────┘  └──────┘  └──────┘  └────────┘  └────────┘
                                                         │
                                              ┌──────────┴──────────┐
                                              │                     │
                                         有进展 + 未达上限      无进展 / 已达标
                                              │                     │
                                              ▼                     ▼
                                       回到 Observe            进入终端状态
```

| 步骤 | 做什么 | 反模式 |
|------|--------|--------|
| **1. Observe**（观察） | 读最新状态，收集可观测证据。不要在过期数据上做决策。 | 用上一轮的缓存继续跑 |
| **2. Choose**（选择） | 从明确的优先级标准中选出本轮最高价值的动作。一次只选一个。 | 试图一次做太多事 |
| **3. Act**（动作） | 做一个有界的、可逆的改动，或产出一个候选方案。 | 一做就是不可逆的大动作 |
| **4. Verify**（验证） | 用可复现的、独立于动作信号的标准检查结果。 | "我觉得可以了"——主观自评 |
| **5. Record**（记录） | 保存本轮的动作、证据、结果、剩余工作。下一轮或下一个接手者能接上。 | 跑完不留痕迹 |
| **6. Repeat or Stop**（循环或停止） | 只要有可测量的进展且未触及上限→继续。否则→进入终端状态。 | 无限循环；或该停不停 |

### 六种终端状态

Loop 不是无限循环——它必须有明确的停止条件。六种终端状态覆盖了所有正常和异常的退出路径：

| 终端状态 | 含义 | 映射到本框架的生命周期拓扑 |
|---------|------|--------------------------|
| **success**（成功） | 可观测的成功标准已达成 | Implicit-termination（自然完成） |
| **clean no-op**（干净空转） | 本轮无可做的事，且预期下一轮也没有 | Implicit-termination（无事可做） |
| **blocked**（阻塞） | 被外部依赖卡住，需要等待或人工介入 | Pause-resume（暂停等待） |
| **approval-required**（需审批） | 下一步是不可逆/破坏性/对外的动作，必须先获得批准 | Escalate（升级到人） |
| **exhausted**（耗尽） | 预算（时间/token/轮数）用完但目标未达成 | Explicit-termination（强制终止） |
| **stagnated**（停滞） | 连续 N 轮无实质性进展——"在转圈但不往前走了" | Explicit-termination（无进展终止） |

**关键原则**：exhausted 和 stagnated **不能**被报告为 success。耗尽或停滞 ≠ 完成。

### Loop 的设计护栏

| 护栏 | 含义 | 映射到本框架 |
|------|------|------------|
| **可观测的成功门** | 用 rubric / 阈值 / 有限场景集 / 评审决策替代"直到满意" | P4 接口类型化 + P6 可观测性 |
| **独立验证** | 创建者和审批者不能是同一人。防止自我肯定偏差。 | Senate 模式的核心机制——多 agent 独立审视 |
| **审批边界** | 破坏性/不可逆/生产环境/财务/隐私/对外消息 → 必须显式批准 | P7 人在关键决策点 + 决策·Escalate |
| **新鲜状态** | 每次重要动作前重读当前状态，不基于过期假设 | Blackboard 通信的拉取语义 |
| **保护无关工作** | 不覆盖、不破坏用户的其他工作 | P5 故障隔离 |
| **分离工作信号与验证信号** | 优化 prompt/模型/排序时，不能用同一个指标既当优化目标又当验收标准——会过拟合 | 执行·Speculative 的验证环路 |

### Loop 与宏观模式的连接

**一个 Loop 的 handoff（交接）就是通信拓扑的实例化：**

```
Loop A 完成 → 输出结构化结果 → handoff → Loop B 的 Observe 收到
                                          │
                                          ▼
                                 这恰好是 Relay Chain 的一个边
                                 或 Orchestrator 的一次路由
                                 或 Blackboard 的一次写入+拉取
```

**Loop 的"独立验证"护栏天然引向多 Agent 模式：**

```
单 Loop 自我验证（弱）          多 Loop 独立验证（强）

┌──────────┐                  ┌──────────┐    ┌──────────┐
│  Loop A  │                  │  Loop A  │    │  Loop B  │
│  创建     │                  │  创建     │    │  独立验证  │
│  + 自评 ✓ │                  │          │    │  (Senate) │
└──────────┘                  └──────────┘    └──────────┘
   ↑ 自我肯定偏差                    │               │
                                    └───────┬───────┘
                                            ▼
                                     ┌──────────┐
                                     │ Orchestrator│
                                     │  综合裁决    │
                                     └──────────┘
```

这就是为什么 **Senate（元老院）模式** 在多 agent 协作中如此重要——它不是凭空设计的，而是从 Loop 的独立验证护栏自然推导出来的。

## L1 · 五维原语空间（宏观层）

从第一性原理和 van der Aalst 工作流模式推导出的完整原语体系。任何多智能体系统 = 五个维度各选一个原语的组合。

### 维度一：通信拓扑（信息如何流动）

| 原语 | 核心特征 | 信息效率 | 耦合度 |
|------|---------|---------|-------|
| **Line** | 信息沿链传递，上游不看下游 | 低（信息被截断） | 低 |
| **Star/Hub** | 信息必须经中心节点路由 | 中（中心是瓶颈） | 中 |
| **Mesh/P2P** | 任意节点可直连 | 高（连接数 O(n²)） | 高 |
| **Tree** | 层级代理，信息沿父子路径 | 中 | 中 |
| **Bus/Broadcast** | 一发全收，不做过滤 | 高（带宽）但不精准 | 最高 |
| **Blackboard** | 写公共空间，按需读取（拉取式） | 最高（按需拉取） | 最低 |

**关键洞察**：群聊 = **Bus 通信**。信息效率高的代价是不精准。Blackboard 是 Bus 的反面——同样是共享空间，但 agent **主动拉取**而非被动接收。

### 维度二：执行拓扑（任务如何调度）

| 原语 | 核心特征 | 何时最优 |
|------|---------|---------|
| **Serial**（链式） | 严格先后顺序 | 下游强依赖上游完整输出 |
| **Parallel**（并行） | Fork→独立执行→Join | 任务完全独立 |
| **DAG**（有向无环图） | 部分有序、部分并行 | 任务间有精确的依赖关系 |
| **Speculative**（投机） | 多条路径同时跑，选最优 | 不确定哪条路对，且试错成本低 |
| **Iterative**（迭代） | 输出循环回输入，逐次精化 | 质量渐进提升，需要"品味判断" |
| **Recursive**（递归） | 任务动态拆出子任务 | 问题规模未知，需要动态分解 |

**打破 DAG 唯一论**：DAG 的前提是你**事先知道完整的依赖关系**。很多任务满足不了这个前提——创意写作用 Iterative，不确定路径用 Speculative，问题规模在展开时才发现用 Recursive。

### 维度三：决策拓扑（冲突如何裁决）

| 原语 | 核心机制 | 适用场景 |
|------|---------|---------|
| **Monarch**（君主） | 单一 agent 拍板 | 有明确专家/权威 |
| **Vote**（投票） | 多数决 | 主观判断（审美、伦理） |
| **Consensus**（共识） | 全票通过 | 高风险安全决策 |
| **Market**（市场） | 出价/竞标分配 | 异构 agent 竞争有限任务 |
| **Escalate**（升级） | 上报人类/上层 | 低置信度或不可逆行动 |

### 维度四：生命周期拓扑（怎么生、怎么死？）✨

| 原语 | 核心机制 |
|------|---------|
| **Implicit-termination** | 无事可做时自然终止 |
| **Explicit-termination** | 到达终止节点时强制终止（无论是否还有活动在执行） |
| **Cancel-activity** | 取消单个活动实例 |
| **Cancel-region** | 取消一组活动（阶段回滚） |
| **Cancel-case** | 终止整个流程实例 |
| **Pause-resume** | 暂停→恢复 |
| **Retry** | 失败后重试 |

### 维度五：约束拓扑（什么条件下能动？）✨

| 原语 | 核心机制 |
|------|---------|
| **Deferred-choice** | 决策推迟，等外部事件/用户决定 |
| **Milestone** | 活动只在特定阶段可用，过期永久关闭 |
| **Critical-section** | 同一时刻只有一个 agent 能访问某个资源 |
| **Interleaved** | 顺序任意但不能同时执行 |
| **Transient-trigger** | 信号瞬时——错过就永久丢失 |
| **Persistent-trigger** | 信号持久——排队等待活动变为可用 |

## L2 · 模式目录（20 个具名模式）

按通信拓扑分族，每个模式给出五维签名、核心机制、最优/失败场景、人组织类比。

### 族一：Line 通信

#### 模式 1 · Relay Chain（接力链）

```
A ───→ B ───→ C
   输出    输出
```

| 维度 | 选择 |
|------|------|
| 通信 | Line |
| 执行 | Serial |
| 决策 | Monarch（每节点在自己步骤内独裁） |
| 生命周期 | Implicit-termination |
| 约束 | 无 |

**机制**：每个 agent 只接收上一个 agent 的结构化输出，完成自己的任务后把结果交给下一个。

**最优**：翻译→润色→排版 类流水线。

**失败**：上游犯错下游无法纠正；中间节点缺乏全局上下文。

**类比**：工厂流水线。

---

#### 模式 2 · Review Chain（审核链）

| 维度 | 选择 |
|------|------|
| 通信 | Line |
| 执行 | Serial |
| 决策 | Vote（隐式——每个审核者都有否决权，"打回"上游重做） |
| 生命周期 | Cancel-activity |
| 约束 | 无 |

**机制**：接力链变体——下游有否决权，可打回上游重做。

**最优**：代码审查、合规审核、学术同行评审。

**失败**：无限打回循环。

**类比**：论文 peer review 多轮。

---

### 族二：Star 通信

#### 模式 3 · Orchestrator（编排者）

```
        ┌──→ B ──┐
   A ───┼──→ C ──┼──→ D
        └──→ E ──┘
   编排者  工人    汇合
```

| 维度 | 选择 |
|------|------|
| 通信 | Star |
| 执行 | DAG |
| 决策 | Monarch |
| 生命周期 | Implicit-termination + Cancel-activity（超时取消） |
| 约束 | 无 |

**机制**：编排 agent 掌握全局 DAG，按依赖关系分发子任务，收集结果后继续路由。即 **Work Graph 模式**。

**最优**：依赖关系事先已知、任务可精确分解。

**失败**：Orchestrator 是单点故障和认知瓶颈。

**对应框架**：LangGraph、Temporal、AWS Step Functions。

**类比**：项目经理 + 甘特图。

---

#### 模式 4 · Dispatcher（分发者）

| 维度 | 选择 |
|------|------|
| 通信 | Star |
| 执行 | Parallel（无依赖，纯并发 Map-Reduce） |
| 决策 | Monarch |
| 生命周期 | Cancel-activity + Complete-multiple-instance |
| 约束 | 无 |

**机制**：Orchestrator 的退化版——任务间无依赖，纯分发-汇总。

**最优**：翻译 N 段独立文本、分析 N 份独立财报。

**类比**：外卖平台派单。

---

#### 模式 5 · Teacher-Student（师生模式）

| 维度 | 选择 |
|------|------|
| 通信 | Star（单向为主，偶有反向反馈） |
| 执行 | Iterative |
| 决策 | Monarch（Teacher 有最终评判权） |
| 生命周期 | Retry（重新生成） |
| 约束 | 无 |

**机制**：Teacher 派任务、评判、给反馈，Student 迭代改进。评判比生成容易时最优。

**最优**：代码生成+代码审查。

**类比**：导师带研究生改论文。

---

### 族三：Bus 通信

#### 模式 6 · Group Chat（群聊）

| 维度 | 选择 |
|------|------|
| 通信 | Bus |
| 执行 | Serial（天然串行） |
| 决策 | 隐式/无结构 |
| 生命周期 | Implicit-termination（自然聊完）/ 无限循环风险 |
| 约束 | 无 |

**机制**：所有人看到所有消息，讨论出一个结果。

**最优**：探索性任务——不确定怎么做、需要多视角碰撞、人类实时介入。

**失败**：上下文爆炸（O(n²)）、无限讨论循环、决策责任模糊。

**对应框架**：AutoGen（经典版）。

**类比**：微信群开会。

---

#### 模式 7 · Town Hall（市政厅）

| 维度 | 选择 |
|------|------|
| 通信 | Bus（讨论阶段） |
| 执行 | Speculative（并行出方案）+ Serial（讨论） |
| 决策 | Vote（结构化投票） |
| 生命周期 | Explicit-termination |
| 约束 | Milestone（投票窗口有时限） |

**机制**：群聊的结构化升级——提案→讨论→**明确投票**终结讨论。

**最优**：创意评选、伦理决策。

**类比**：学术委员会答辩+投票。

---

#### 模式 8 · Debate（辩论）

| 维度 | 选择 |
|------|------|
| 通信 | Bus（辩论发言）+ Star（裁判接收输出） |
| 执行 | Iterative（多轮） |
| 决策 | Monarch（裁判裁决） |
| 生命周期 | Explicit-termination |
| 约束 | Deferred-choice |

**机制**：双方被分配对立立场，交替发言互相反驳，裁判全程沉默最后裁决。

**最优**：安全评估、策略选型、红队蓝队对抗验证。

**失败**：辩论退化为语义纠缠。

**类比**：法庭辩论。

---

### 族四：Blackboard 通信

#### 模式 9 · Classic Blackboard（经典黑板）

| 维度 | 选择 |
|------|------|
| 通信 | Blackboard |
| 执行 | Parallel（多 agent 并发读写黑板） |
| 决策 | Monarch（Controller 决定何时停止） |
| 生命周期 | Implicit-termination（黑板稳定） |
| 约束 | Critical-section（写同一区域需加锁） |

**机制**：所有 agent 共享知识空间，每个 agent 监控变化，发现自己能贡献的部分就拉取→处理→写回。**没有谁派活——agent 靠黑板上的机会自我激活。**

**最优**：问题结构未知、需要不同专长逐步拼出答案——医疗诊断、故障排查。

**失败**：agent 争抢同一区域；某些 agent 永远不被激活。

**经典出处**：1970s Hearsay-II 语音理解系统。

**类比**：白板上的脑暴。

---

#### 模式 10 · Market Board（市场黑板）

| 维度 | 选择 |
|------|------|
| 通信 | Blackboard（任务发布）+ Star（认领确认） |
| 执行 | Parallel |
| 决策 | Market（agent 竞标任务） |
| 生命周期 | Cancel-activity（无人认领超时取消） |
| 约束 | Deferred-choice |

**机制**：黑板上的不是"知识碎片"而是"待认领的任务"。Agent 评估自己能力和成本，出价竞标。

**最优**：异构 agent 池，任务无法完美预匹配。

**类比**：Upwork 自由职业平台。

---

#### 模式 11 · Auction House（拍卖行）

| 维度 | 选择 |
|------|------|
| 通信 | Blackboard |
| 执行 | Speculative（多 agent 对同一任务出方案） |
| 决策 | Market（按质量竞争） |
| 生命周期 | Cancel-activity（落选方案丢弃） |
| 约束 | Milestone + Critical-section |

**机制**：让多个 agent 对**同一个任务**出方案，选最优，其余丢弃。

**最优**：方案质量方差大、试错成本低的创意任务。

**类比**：设计竞标——三家设计公司各出一稿。

---

### 族五：Mesh 通信

#### 模式 12 · Swarm（蜂群）

| 维度 | 选择 |
|------|------|
| 通信 | Mesh（每节点只与邻居通信） |
| 执行 | Parallel（大量简单 agent） |
| 决策 | Emergent（涌现——无显式决策者） |
| 生命周期 | Implicit-termination（全局稳定） |
| 约束 | 无 |

**机制**：大量简单 agent，每个只遵循局部规则，复杂行为从局部交互中**涌现**。

**最优**：大规模模拟、分布式搜索、需要 scalability 远超单点编排的场景。

**失败**：涌现行为不可预测、收敛时间不确定。

**类比**：蚁群、鸟群。

---

#### 模式 13 · Hive Mind（集体意识）

| 维度 | 选择 |
|------|------|
| 通信 | Mesh（P2P 同步）+ Blackboard（共享账本） |
| 执行 | Iterative（同步→独立工作→再同步） |
| 决策 | Consensus（写入需多数确认） |
| 生命周期 | Implicit-termination |
| 约束 | Critical-section（写入账本需共识锁） |

**机制**：Swarm 升级版——有分布式共享状态（账本/知识图谱），每次写入需共识确认。

**最优**：分布式知识构建。

**类比**：Wikipedia 编辑社区。

---

#### 模式 14 · Gossip Protocol（八卦协议）

| 维度 | 选择 |
|------|------|
| 通信 | Mesh（随机 P2P，无固定拓扑） |
| 执行 | Parallel（信息扩散） |
| 决策 | 无（只传信息不做决策） |
| 生命周期 | Implicit-termination |
| 约束 | 无 |

**机制**：每个节点随机选邻居交换信息，信息像病毒一样去中心扩散。

**最优**：信息同步类任务。

**失败**：收敛慢；信息在传播中变形。

**类比**：茶水间八卦。

---

### 族六：Tree 通信

#### 模式 15 · Hierarchy（层级制）

| 维度 | 选择 |
|------|------|
| 通信 | Tree |
| 执行 | DAG（层内）+ Recursive（拆分到下层） |
| 决策 | Escalate（下层搞不定→升级） |
| 生命周期 | Cancel-region |
| 约束 | Milestone（每层阶段门） |

**机制**：顶层拆目标→中层再拆→底层执行→层层汇总。搞不定的逐级升级。

**最优**：需要可解释性和责任归属的大规模任务。

**类比**：军队/大公司。

---

#### 模式 16 · Federation（联邦制）

| 维度 | 选择 |
|------|------|
| 通信 | Tree（联邦层↔各州）+ 各州内部任意 |
| 执行 | Parallel（各州独立） |
| 决策 | Vote（联邦层）+ Monarch（州内） |
| 生命周期 | Cancel-activity（单州内取消不影响其他州） |
| 约束 | Milestone |

**机制**：多个自治团队各自运作，联邦层只处理跨域冲突和全局资源配置，不做日常决策。

**最优**：多个相对独立的工作域需要偶尔协同。

**类比**：欧盟。

---

#### 模式 17 · Divide-and-Conquer（分治）

| 维度 | 选择 |
|------|------|
| 通信 | Tree |
| 执行 | Recursive（递归拆分直到原子大小） |
| 决策 | Monarch（父节点决定如何拆） |
| 生命周期 | Retry（子问题求解失败→重新拆分） |
| 约束 | 无 |

**机制**：问题递归拆分——能解则解，不能则拆。叶子求解，结果层层合并。

**最优**：问题规模在展开前未知——代码迁移、大规模数据清洗。

**类比**：归并排序算法。

---

### 族七：混合拓扑

#### 模式 18 · Senate（元老院）

| 维度 | 选择 |
|------|------|
| 通信 | Star（各专家只与议长通信，互相不通信） |
| 执行 | Parallel + Speculative（各专家独立同时出方案） |
| 决策 | Monarch（议长综合） |
| 生命周期 | Cancel-activity（超时不等） |
| 约束 | Deferred-choice + Milestone |

**机制**：专家之间**不互相看对方的输出**（防羊群效应）。每个专家独立审视同一问题写意见书。议长读完全部后综合。

**与 Group Chat 的本质区别**：群聊让所有人看到所有人的中间想法（羊群效应 risk）。Senate 要求先独立、再综合。

**最优**：需要多视角但视角之间容易互相污染——策略评估、伦理审查。

**类比**：最高法院。

---

#### 模式 19 · Matrix（矩阵组织）

| 维度 | 选择 |
|------|------|
| 通信 | Tree（功能线）+ Mesh（项目线交叉） |
| 执行 | Parallel（多项目并发） |
| 决策 | Escalate（冲突升级） |
| 生命周期 | Cancel-region |
| 约束 | Critical-section（同一 agent 不能同时被两个任务占用） |

**机制**：Agent 按功能组织但同时分配到不同项目。每个 agent 有两个协调线——功能主管管"怎么做"，项目主管管"做什么"。

**最优**：需要专业分工 + 跨职能项目协作。

**类比**：大公司矩阵管理。

---

#### 模式 20 · Hollywood Model（好莱坞模式）

| 维度 | 选择 |
|------|------|
| 通信 | Star（制片人协调） |
| 执行 | Speculative + Iterative |
| 决策 | Monarch（制片人拍板） |
| 生命周期 | Explicit-termination（项目完工=团队解散） |
| 约束 | Milestone |

**机制**：围绕单个项目临时组建专门的 agent 团队。制片人选角→各角色独立创作→多轮修改→项目结束团队解散。

**最优**：一次性、定制化的复杂任务，每次需要的 agent 组合都不同。

**类比**：电影制作。

## L3 · 决策矩阵

### 决策维度：评估一个任务该问的 8 个问题

| # | 维度 | 问题 | 答案类型 |
|---|------|------|---------|
| D1 | **依赖已知性** | 全部子任务之间的依赖关系，你在开始执行前就知道吗？ | 是 / 部分是 / 否 |
| D2 | **并行潜力** | 有多少子任务可以同时执行而不互相干扰？ | 高 / 中 / 低 |
| D3 | **质量敏感度** | 一个子任务的错误会导致整个结果不可用吗？ | 致命 / 可容忍 / 无关 |
| D4 | **解空间清晰度** | 存在唯一正确解，还是多个路径都可能"算对"？ | 唯一解 / 多路径 / 完全开放 |
| D5 | **Agent 异质性** | Agent 之间能力和知识差异大吗？还是可以互换？ | 高度异质 / 中度差异 / 完全同质 |
| D6 | **任务规模** | 大概有多少个子任务单元？ | 少量(<10) / 中量(10-100) / 大量(>100) |
| D7 | **不可逆性** | 执行过程中存在不可逆的动作吗？ | 有不可逆步骤 / 全部可回滚 |
| D8 | **人类参与度** | 人需要实时观察、中途干预、还是只需看最终结果？ | 实时参与 / 关键决策点 / 只看结果 |

### 模式 ↔ 任务类型速查表

| 你的任务 | 推荐模式 | 关键原因 |
|---------|---------|---------|
| 翻译→校对→排版 | **接力链** | D1=是, D2=低, 线性管道 |
| 分析 N 份独立财报 | **分发者** | D1=是, D2=高, 独立并行 |
| 复杂后端开发（API+DB+前端） | **编排者** | D1=是, D2=高, 有依赖 DAG |
| 代码生成+审查+修改 | **师生模式** | D3=致命, 评判容易生成难 |
| 安全漏洞审计 | **辩论** | D3=致命, 需要对抗性验证 |
| 策略方案三选一 | **元老院** | D4=多路径, 防羊群效应 |
| 创意文案生成 | **拍卖行** | D4=多路径, 多方案竞标 |
| 故障根因分析 | **经典黑板** | D4=开放, D1=否, 逐步拼图 |
| 对话式心理分析（探索期） | **群聊** → **Orchestrator**（稳定后） | D4=开放, D8=实时 |
| 大规模代码迁移 | **分治法** | D1=部分是, D6=大量, 递归拆分 |
| 跨部门合规审查 | **联邦制** | D5=高异质, 各域自治 |
| 新产品多专家评审 | **元老院** | D4=多路径, 防互相污染 |
| 每天定时生成报表 | **分发者** | D1=是, D2=高, 稳态流程 |
| 实时客服+人可接管 | **群聊 + Escalate** | D8=实时, D7=有不可逆 |

### 模式切换原则

真实系统应该在执行过程中切换模式：

```
探索阶段              稳定阶段              优化阶段
   │                     │                     │
   ▼                     ▼                     ▼
┌────────┐          ┌──────────┐          ┌──────────┐
│ Group  │   ──→    │Orchestrator│  ──→    │Dispatcher │
│ Chat   │  摸清    │ (DAG)    │  固化    │ (Parallel)│
│        │  依赖后  │          │  为模板后│           │
└────────┘          └──────────┘          └──────────┘
  人类在回路           人类只在             全自动
                      关键决策点
```

群聊不是没用的——它是**最佳探索工具**。Orchestrator 发现 DAG 未覆盖的状况时，应能**降级到群聊**求助人类。

## 案例应用：星灵项目

### 当前架构（单 agent 接力链）

```
输入 → Step0(触发判定) → Step1(看见双方) → Step2A/2B(分轨) → Step3(出门体检) → 输出
```

当前在 D1-D8 评估下合理——整个流水线在一个 LLM 调用中完成，不存在"多 agent"。

### 未来多 agent 架构选型

| 维度 | 评估 |
|------|------|
| D1 依赖已知性 | **是** — 感知→洞察→行动，依赖链清晰 |
| D2 并行潜力 | **中** — 感知和部分洞察可并行 |
| D3 质量敏感度 | **致命** — 错误洞察 = 伤害用户 |
| D4 解空间 | **多路径** — 同一对话可有诊断或鼓励切入角 |
| D5 Agent 异质性 | **中** — 不同引擎能力不同但不极端 |
| D7 不可逆性 | **有** — 弹窗展示给用户 = 不可逆 |
| D8 人类参与度 | **只看结果** — 最终用户看到弹窗 |

**推荐**：**Orchestrator（编排者）+ Senate（元老院）混合**

```
                  对话输入
                     │
                     ▼
            ┌───────────────┐
            │  Orchestrator  │  ← 编排 agent 掌握整体流程
            └───┬───┬───┬───┘
                │   │   │
       ┌────────┘   │   └────────┐
       ▼            ▼            ▼
   ┌────────┐ ┌────────┐ ┌──────────┐
   │ 感知    │ │ 洞察    │ │ Step3     │
   │ agent  │ │ agent  │ │ 出门体检   │
   │(1A+1B) │ │(2A/2B) │ │ agent     │
   └───┬────┘ └───┬────┘ └─────┬─────┘
       │          │            │
       └──────────┴────────────┘
                │
                ▼
           弹窗输出（人类看到的最终结果）
```

关键增强：在**信念方向判断模糊**时（分不清该走鼓励还是诊断），Orchestrator 可以临时切换为 **Senate**——让感知 agent 和洞察 agent **独立**给出判断，Orchestrator 综合，防止一个 agent 的偏见污染另一个。

**群聊的角色**：开发调试阶段用——所有 agent 中间推理输出到共享日志，开发者像看"群聊记录"一样理解每个 agent 在想什么。

## 两层统一：Loop 是原子，Pattern 是分子

### 全景图

```
┌──────────────────────────────────────────────────────────┐
│                    宏观层 · 协作拓扑                        │
│  （本框架的 20 个模式）                                     │
│                                                          │
│  ┌───────┐   ┌───────┐   ┌───────┐                       │
│  │ Loop  │   │ Loop  │   │ Loop  │   ← 每个节点是一个 loop  │
│  │  A    │──→│  B    │──→│  C    │                       │
│  └───────┘   └───────┘   └───────┘                       │
│      │           │           │                            │
│  ┌───┴───────────┴───────────┴──────────────────────┐    │
│  │         通信拓扑 · 执行拓扑 · 决策拓扑              │    │
│  │         生命周期拓扑 · 约束拓扑                     │    │
│  └──────────────────────────────────────────────────┘    │
│                                                          │
├──────────────────────────────────────────────────────────┤
│                    微观层 · 循环执行                        │
│  （loop-library 的六步心跳）                               │
│                                                          │
│  ┌──────────────────────────────────────────────────┐   │
│  │  Observe → Choose → Act → Verify → Record → ...   │   │
│  │     ↑                                      │       │   │
│  │     └─────────── 反馈 ─────────────────────┘       │   │
│  │                                                    │   │
│  │  终端状态: success | no-op | blocked | approval   │   │
│  │           | exhausted | stagnated                  │   │
│  └──────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────┘
```

### 概念映射总表

| 微观层（Loop） | 宏观层（本框架） | 关系 |
|---------------|-----------------|------|
| **Observe → Choose → Act → Verify** | 执行·Serial（一个 agent 内部的微串行） | Loop 是 Serial 在单 agent 内部的展开 |
| **Record + Repeat or stop** | 执行·Iterative | 同一概念，不同粒度 |
| **六种终端状态** | 生命周期拓扑（Implicit/Explicit/Cancel/Escalate/Pause） | 精确映射——Loop 的终端状态就是生命周期维度的具体取值 |
| **Handoff** | 通信拓扑（Line / Star / Blackboard / Bus / Mesh / Tree） | Loop 的 handoff 是通信原语的实例化 |
| **独立验证** | Senate 模式 / Debate 模式 | 同构——"创建和审批不能同一人"正是 Senate 的多 agent 独立审视 |
| **审批边界** | 决策·Escalate + 约束·Deferred-choice | 同一安全原则在两个层级的表达 |
| **新鲜状态** | Blackboard（拉取式读最新） | Loop 的"重读当前状态"就是 Blackboard 的前提 |
| **无进展停止** | 生命周期·Explicit-termination | 不设死上限，靠 stagnated → 停止 |
| **六步心跳** | ❌ 本框架未展开（只有一个"Serial"太粗） | Loop 补上了本框架缺失的微观层 |
| **循环发现/审计** | ❌ 本框架完全没有 | Loop 独有的方法论 |

### 互补性

| | Loop Library 有，本框架缺 | 本框架有，Loop Library 缺 |
|---|--------------------------|--------------------------|
| **微循环设计** | ✅ 六步心跳 + 六种终端状态 + 护栏 | ❌ 本框架的 Serial 太粗 |
| **循环发现** | ✅ 从代码库/历史挖掘隐性循环 | ❌ 无 |
| **循环审计** | ✅ Loop Doctor 诊断修复 | ❌ 无 |
| **通信拓扑分类** | ⚠️ 只有 handoff | ✅ 六种拓扑 + 各自适用场景 |
| **执行拓扑分类** | ❌ 无（Loop 是单 agent 的） | ✅ DAG / Speculative / Recursive 等 |
| **决策拓扑分类** | ❌ 无 | ✅ Monarch / Vote / Consensus / Market / Escalate |
| **模式目录** | ❌ 无 | ✅ 20 个具名模式 + 决策矩阵 |
| **模式切换策略** | ❌ 无 | ✅ 探索→群聊→DAG→Dispatcher |

### 实操：设计一个多 Agent 系统的两步法

```
Step 1（宏观）：用本框架的决策矩阵选协作模式
               ↓
Step 2（微观）：用 Loop 的六步心跳设计每个 agent 的内部循环
               ↓
Step 3（接口）：Loop 的 handoff = 宏观通信拓扑的实例化
               （带类型签名的结构化输出）
```

**对星灵的实战映射：**

| 层级 | 用哪个 | 做什么 |
|------|-------|--------|
| 宏观 | 本框架的 **Orchestrator + Senate 混合** | 编排感知/洞察/行动 agent 的协作关系 |
| 微观 | Loop 的 **六步心跳** | 设计每个 agent 的内部执行质量（观察→选择→动作→验证→记录→停止） |
| 接口 | Loop 的 **handoff** + 本框架的 **P4 类型化接口** | 感知 agent 输出结构化 JSON → 洞察 agent 接收 |

## 核心结论

1. **群聊不是主流生产模式**，因为它违反信息最小化、最大化并行、接口类型化、故障隔离、可观测性——5/7 条第一性原理。但它是**最佳探索工具**。

2. **DAG 编排是最优的稳态执行模式**，但不是唯一的。20 个具名模式各有其不可替代的甜区。

3. **五维原语空间**（通信 × 执行 × 决策 × 生命周期 × 约束）构成了任何多智能体协作系统的完整设计语言。

4. **模式应该切换**——探索→群聊，稳定→DAG，优化→Dispatcher。成熟的框架不应绑死在一种模式上。

5. **Senate（元老院）是一个被严重低估的模式**——它在防羊群效应和多视角独立性上，同时优于群聊和一 agent 自我反思。

6. **两层统一**：Loop（微观六步心跳）是原子，Pattern（宏观 20 个模式）是分子。Loop 描述一个 agent 怎么做好自己的事，Pattern 描述多个 agent 怎么配合。两者从同一组第一性原理推导，在概念上有精确同构映射。合并后形成完整的 agent 系统设计理论。
