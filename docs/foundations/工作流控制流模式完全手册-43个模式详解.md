## 概述：这套模式是什么

1999 年，荷兰计算机科学家 Wil van der Aalst 和他的合作者发现了一个尴尬的局面：每一家工作流引擎（IBM、BEA、Oracle、Staffware、COSA……）都定义了自己的"基础动作"集合——但没有任何公约数。你要比较两个引擎谁更强，你连"更强的标准"是什么都说不清。

他们做了一件很"计算机科学家"的事：**先不看软件，而是收罗了数百个真实的业务流程，然后问——人类描述工作流时，在语法层面到底需要哪些"动作"？**

从这些真实案例中，他们提炼出 20 个模式。2006 年，基于更严格的着色 Petri 网（CPN）形式化，将体系扩展为 **43 个控制流模式**。

这套模式的意义不在"多"——而在于它是一种**正交语言**：每个模式解决一类独立的结构需求，不是某个厂商一拍脑袋造的轮子。至今仍被用来评估 BPMN、BPEL、UML Activity Diagram、XPDL、YAWL 等建模语言的表达能力——**一个建模语言能覆盖多少个 workflow pattern，就等于它能表达多复杂的真实流程。**

在智能体编排的语境下，这套词汇相当于**编排领域的元素周期表**。

## 第1类：基础控制流（WCP1–5）

最基本的流程控制——所有的编排逻辑最终都可以分解为这五种动作的组合。

---

### WCP1 — Sequence（顺序）

**中文名称：** 顺序执行

**一句话定义：** 在流程中的同一个线程内，活动 B 必须在活动 A 完成之后才能启动。

**形式语义：** 活动 A 终止后，在 A 的输出位置产生一个 token，该 token 被 B 消费，B 被使能（enabled）。

**Petri 网表示：** 最基本的「位置→变迁→位置」结构。

**编排中的含义：** 所有工作流的最小公分母。任何编排工具都在用。对应 LangGraph 的 `add_edge("A", "B")`（无条件的顺序边）。

**反常识点：** 顺序表面上看最简单，但它隐含了一个最强的假设——**B 对 A 的全量因果依赖**。你把两个东西串起来的那一刻，你已经断言了"A 的输出是 B 的唯一入口"，而这个断言在分布式环境下很可能为假。

---

### WCP2 — Parallel Split（并行分叉 / AND-split）

**中文名称：** 并行分叉

**一句话定义：** 流程中的一个点，在此处，单一线程的控制被分裂成多个并行执行的线程。

**形式语义：** 活动 A 完成后，A 的输出位置产生一个 token。变迁 AND-split 消费这个 token 后，向所有后续活动的输入位置各产生一个 token。B 和 C 同时被使能。

**编排中的含义：** 多个 agent 同时启动，互不相干。对应 LangGraph 的 `Send` API——从一个节点向多个目标节点发送并行消息。

**实例：** 订单完成后，同时触发"通知仓库"和"发送确认邮件"两条并行线。

---

### WCP3 — Synchronization（同步汇合 / AND-join）

**中文名称：** 同步汇合

**一句话定义：** 流程中的一个点，在此处，多条并行执行的线程汇合成一条单一的控制线程——只有当所有进入的线程都完成时，下游才会启动。

**形式语义：** AND-join 变迁只有在每个输入位置都至少有一个 token 时才会被使能。一旦使能，它从每个输入位置消费一个 token，并向下游位置产生一个 token。

**编排中的含义：** 等所有并行 agent 的结果都回来之后再往下走。这是编排里最痛苦的瓶颈——**你永远在等最慢的那个人**。

**实例：** 等到"仓库发货确认"和"客户收到邮件"都确认后，才将订单状态改为"已完成"。

---

### WCP4 — Exclusive Choice（排他选择 / XOR-split）

**中文名称：** 排他选择

**一句话定义：** 流程中的一个点，在此处，基于一个决策或工作流控制数据，从若干可选分支中**恰好选择一个**。

**形式语义：** 活动 A 完成后，对每一个后续变迁都给出使能条件。恰好一个变迁的使能条件为真，该变迁消费 A 的 token 并只向所选分支产生一个 token。

**编排中的含义：** 路由/分流。根据 LLM 输出决定下一步走哪个 agent。对应 LangGraph 的 `add_conditional_edges`。

**实例：** 审核结果若为"通过"→进入签约流程；若为"驳回"→进入申诉流程。两个分支不可能同时走。

---

### WCP5 — Simple Merge（简单合并 / XOR-join）

**中文名称：** 简单合并

**一句话定义：** 流程中的一个点，在此处，两个或更多可选分支汇合在一起，不进行任何同步——**假设这些分支中只有一个会被激活**。

**形式语义：** 任何一个分支完成后，其 token 立即使能后续活动。由于独占选择只激活一条分支，所以恰好有一个 token 到达，下游被触发恰好一次。

**编排中的含义：** 排斥性路由的另一端——多个分支的出口合到同一个下游节点。

**注意事项：** 这个模式**假设只有一个分支会被激活**。如果上游可能激活多条分支，请使用 WCP7（同步合并）或 WCP8（多重合并）。如果多条 token 意外到达，简单合并会产生竞态条件——谁先到谁触发，后续的 token 会丢失或导致未定义行为。

## 第2类：高级分叉与同步（WCP6–9, 28–33, 37–38, 41–42）

这些模式处理了"不止一条，但不是所有"分支——AND 和 XOR 之间的灰色地带。

---

### WCP6 — Multi-Choice（多选分叉 / OR-split）

**中文名称：** 多选分叉

**一句话定义：** 流程中的一个点，在此处，基于一个决策或工作流控制数据，**若干条分支被选中**（最少一条，最多全部）。

**形式语义：** 活动 A 终止后，对每个输出分支独立评估条件。对每个条件为真的分支，向该分支产生一个 token。A 的触发在**所有被选分支都被使能后**才正式终止。

**与 WCP4 的区别：**

| 维度 | WCP4（排他） | WCP6（多选） |
|------|:----------:|:----------:|
| 选择数量 | 恰好 1 条 | 1 到 N 条 |
| 条件评测 | 互斥 | 独立 |
| 下游并发 | 否 | 是 |

**实例：** 紧急事件响应中，系统同时评估：「有火情→派消防」、「有伤员→派救护车」、「有犯罪→派警察」。可能 0 到 3 条同时激活。

---

### WCP7 — Structured Synchronizing Merge（结构化同步合并）

**中文名称：** 结构化同步合并

**一句话定义：** 多条路径汇合为一条线程。如果多条路径被激活，则需要**等所有激活的路径都完成**再往下走；如果只有一条路径被激活，则不需同步，直接通过。

**形式语义：** 每一枚到达的 token 被登记。汇合点只在**所有在对应分叉点被激活的分支**都产出 token 后才触发。这要求它能"知道"上游激活了多少条分支——在结构化版本中，这是由对应的 Multi-Choice 直接传递的。

**关键约束：**
- 已经被激活的分支在汇合等待期间**不可以被再次激活**
- 它必须与一个明确的 Multi-Choice 配对（结构化约束）

**实例：** 紧急事件调度——如果只有消防派出，消防完成后直接进入结案；如果消防、救护都派出，等两者都完才进入结案。

**变体：**
| 编号 | 变体 | 区别 |
|------|------|------|
| WCP37 | 本地同步合并（Local Sync. Merge） | 同步数量由本地可用信息决定 |
| WCP38 | 全局同步合并（General Sync. Merge） | 可以判断某些分支"永远不再可能到达"，不等它们了 |

---

### WCP8 — Multi-Merge（多重合并）

**中文名称：** 多重合并

**一句话定义：** 两条或更多分支汇合，**没有同步**——如果多条路径被激活，**下游活动被每条到达的 token 分别触发一次**。

**形式语义：** 每一枚到达 Multi-Merge 节点的 token 都独立地、不受阻碍地通过，下游活动被使能 N 次（N = 实际到达该位置的分支数）。下游的多个实例可能并发执行。

**与 WCP5、WCP7 的区别：**

| | WCP5（简单合并） | WCP7（同步合并） | WCP8（多重合并） |
|---|---|---|---|
| 触发次数 | 1 次 | 1 次 | N 次 |
| 是否等待 | 否 | 等所有激活分支 | 否 |
| 并发的下游 | 否 | 否 | 是 |

**实例：** 建筑项目管理——「打地基」「订购材料」「预约工人」并行执行，每完成一个就触发一次「质量审查」。

---

### WCP9 — Structured Discriminator（结构化鉴别器）

**中文名称：** 结构化鉴别器

**一句话定义：** 一个汇合点，等待**最先到达的那条分支**完成后即触发下游活动，但继续等待其余分支完成并**吸收**它们（不再触发下游）。当所有分支都到达后，自动**复位**，为下一次循环做好准备。

**形式语义（状态机视角）：**
1. 鉴别器进入等待状态，计数器 = 0，预期数 = N
2. 当一条分支到达：
   - 如果计数器 = 0：**触发下游**，计数器 + 1
   - 如果计数器 > 0：只计数器 + 1
3. 当计数器 = 预期数：**复位**，计数器 = 0（等待下一轮触发）

**关键特性：** 「先到先得」+「后续吸收」+「复位等待下轮」——这使得它可以在循环中使用。

**实例：** 向 3 家供应商询价——第一家报价后立即触发「评估报价」，后两家到的也只记录不重复触发；3 家到齐后复位，下一轮询价可用。

**变体：**
| 编号 | 变体 | 行为区别 |
|------|------|---------|
| WCP28 | 阻塞鉴别器（Blocking Discriminator） | 下游完成前不接收新 token |
| WCP29 | 取消鉴别器（Cancelling Discriminator） | 第一条完成后直接取消其余活跃分支 |
| WCP30 | 结构化部分汇合（Structured Partial Join） | 等 N/M 条完成就触发（通用化鉴别器） |
| WCP31 | 阻塞部分汇合（Blocking Partial Join） | 部分汇合 + 阻塞语义 |
| WCP32 | 取消部分汇合（Cancelling Partial Join） | 部分汇合 + 触发后取消剩余分支 |
| WCP33 | 广义 AND-Join（Generalised AND-Join） | 等所有分支完成，但对 N 的判断可以来自任意上游 |

---

### WCP41 — Thread Merge（线程合并）

**中文名称：** 线程合并

**一句话定义：** 在流程的一个点，**同一分支内**若干并行线程被合并为一个单一控制线程。

**与 WCP3（同步汇合）的区别：** WCP3 合并的是不同分支中的线程；WCP41 合并的是**同一分支内**被 WCP42 分裂出的线程。

**实例：** 某个审批流程中，两位审批人在同一分支内独立审阅，两人审完合成一条意见进入下一步。

---

### WCP42 — Thread Split（线程分叉）

**中文名称：** 线程分叉

**一句话定义：** 在流程的一个点，**同一分支内**指定数量的并行线程被创建。

**与 WCP2（并行分叉）的区别：** WCP2 创建的是多个不同分支（每个有独立后续）；WCP42 在**同一分支内**产生多线程（共享同一后续上下文）。

## 第4类：多实例模式（WCP12–15, 34–36）

多实例模式处理"同一个任务需要创建 N 份副本并行执行"的场景。这些模式按两个维度分类：

**维度一：是否需要同步？**
- WCP12：不同步，下游立即开始
- WCP13–15：同步，等所有实例完成

**维度二：N 是什么时候确定的？**
- WCP13：设计时就写死了
- WCP14：运行前确定（如从订单行数读取）
- WCP15：运行中动态追加

---

### WCP12 — Multiple Instances without Synchronization

**中文名称：** 无同步多实例

**一句话定义：** 多个实例被创建且独立并发执行，**下游活动在实例被创建后立即被使能**，不等它们完成。

**关键行为：**
- 任务 B 产生 N 个实例 (b₁, b₂, …, bₙ)
- 任务 C 在实例们**刚一被启动后**就开始——不等它们结束
- B 的实例可能与 C **重叠执行**

```
     ┌── b₁（仍在跑）──┐
A ─► B ── b₂ ───────────► C（已在执行）
     └── b₃（仍在跑）──┘
         ↑ 实例被使能     ↑ C 立即被使能
```

**后果：** 你无法保证所有 B 实例在流程结束时已完成。流程的终态完备性（soundness）可能被破坏。

**实例：** 用户买了 N 本书——每本书触发一个「处理订单」实例——「发送确认邮件」在订单被分发后立刻发出，不等各个订单实例完成。

---

### WCP13 — Multiple Instances with a priori Design-Time Knowledge

**中文名称：** 设计时已知数量的同步多实例

**一句话定义：** N 在设计时已经确定（硬编码在模型里），所有实例并发执行，等**所有实例完成**后才触发下游。

**实例：** 「年报必须由六位董事全部签字后才能发布」——N = 6 写死在流程模型里。

**BPMN 实现：** Multi-instance loop marker (`|||`)，loop cardinality 为固定数值。

**编排类比：** 你预先知道需要调用几个 agent，写死在配置里。

---

### WCP14 — Multiple Instances with a priori Run-Time Knowledge

**中文名称：** 运行时已知数量的同步多实例

**一句话定义：** N 在设计时未知，但在**第一个实例被创建之前**就确定了。确定后 N 固定不变。所有实例完成后同步。

**N 的来源：**
- 流程数据：`NrOfInstances = GetNumberOfLineItems(order)`
- 资源可用性
- 跨流程通信
- 运行时的用户决策

**实例：** 「审阅一篇论文时，评审任务根据论文内容、审稿人可用性和作者资历创建若干实例。只有当所有审稿意见返回后，处理才继续。」

**BPMN 实现：** Multi-instance marker + 表达式（如 `count = ${lineItems.size()}`）。

**编排类比：** 根据输入的条数决定并行调用 agent 的数量——在输入到达时 N 就确定了。

---

### WCP15 — Multiple Instances without a priori Run-Time Knowledge

**中文名称：** 运行时动态追加的同步多实例

**一句话定义：** N 在**实例已经开始执行后**仍可能变化——新的实例可以在已有实例执行中被动态追加。直到不再有新实例加入，且所有实例完成，才触发同步。

**与 WCP14 的关键区别：** WCP14 在第一个实例启动后 N 就锁定了；WCP15 允许在执行中随时追加。

**实例：** 「将石油钻井平台从工厂运到现场——初始配送任务的估算数量被启动，但如果运力不足，随时可以启动额外的运输任务。全部运输完毕后才能开始组装。」

**编排类比：** 一个 agent 在执行中发现需要额外调用新的子 agent，动态追加到并行池中——LangGraph 的 `Send` + 动态条件判断。

---

### WCP34 — Static Partial Join for Multiple Instances

**中文名称：** 多实例静态部分汇合

**一句话定义：** N 个实例，只需要其中 M 个完成即可触发下游（M < N 且 M 在第一个实例开始时已知），其余 N–M 个实例的结果被忽略。

**与 WCP13 的关系：** WCP13 是 M = N 的特例。

---

### WCP35 — Cancelling Partial Join for Multiple Instances

**中文名称：** 多实例取消部分汇合

**一句话定义：** 同 WCP34，但当 M 个完成后，**其余 N–M 个实例被主动取消**而非继续运行。

---

### WCP36 — Dynamic Partial Join for Multiple Instances

**中文名称：** 多实例动态部分汇合

**一句话定义：** 所需要的完成数量 M 在运行前未知——每完成一个实例就检查终止条件，条件满足即触发下游。此时不允许再创建新实例，剩余实例的结果被忽略。

## 第5类：状态模式（WCP16–18, 39–40）

这些模式不是关于"走向哪儿"——而是关于"在什么条件下可以走"。它们引入了**外部状态**对流程行为的影响。

---

### WCP16 — Deferred Choice（延迟选择）

**中文名称：** 延迟选择

**一句话定义：** 分叉点的选择**不基于流程内部数据**，而是推迟到由外部事件或用户决定——哪条路径先被触发就走哪条。

**与 WCP4（排他选择）的本质区别：**

| | WCP4（排他选择） | WCP16（延迟选择） |
|---|---|---|
| 决策依据 | 流程内部数据 | 外部事件/用户动作 |
| 决策时机 | 在分叉点当下 | 推迟到外部信号到来 |
| 决策者 | 流程引擎 | 外部世界 |

**形式语义（YAWL 的实现）：** 通过一个隐藏的"选择区域"，各个分支被使能但不执行，等待外部信号——先收到信号的分支执行，其余被禁用。

**编排类比：** LangGraph 的 `interrupt` + `Command(resume=...)`——流程暂停等待人的输入，人的输入决定了走哪条分支。

**实例：**
- 一个待办项被分配给两个角色——谁先点"接单"就归谁
- 客户订单——客户可能在 24 小时内取消，也可能确认；系统不替客户做决定，只等

---

### WCP17 — Interleaved Parallel Routing（交错并行路由）

**中文名称：** 交错并行路由

**一句话定义：** 一组活动必须以**任意顺序**执行，但**不能同时执行**（同一时刻最多一个在执行）。且它们的执行顺序**有部分偏序约束**。

**形式语义：** 各活动的使能条件是：没有其他同组的活动正在执行中（互斥）。每个活动恰好执行一次。所有活动执行完毕后，才能进入下游。

**实例：** 申请审批中最怕"串通"——审批 A 不能在审批 B 看到结果之前做出判断。但它们可以任意顺序进行：A 先审 B 后审，或 B 先审 A 后审——只要不并行。

**与 WCP40 的区别：** WCP40 无任何偏序约束；WCP17 有偏序约束。

---

### WCP18 — Milestone（里程碑）

**中文名称：** 里程碑

**一句话定义：** 一个活动**只有在流程处于某个特定状态（阶段）时**才可以被执行。一旦流程过了这个里程碑，该活动就**永久不可用**。

**形式语义：** 该活动的使能条件包含一个状态谓词。当流程从里程碑前的阶段过渡到里程碑后的阶段时，该谓词从 true 变为 false——活动被禁用。任何已使能但尚未执行的实例被撤销。

**编排类比：** Agent 设计中的"门控"——某些工具只能在特定阶段调用。比如"申诉"只在一审和二审之间可用，二审一过就永久关闭。

**实例：**
- 机票预订——付费前可以改签，付费后不行
- 保险理赔——在"定损报告出具前"可以上传补充材料，出具后不能再传

---

### WCP39 — Critical Section（临界区）

**中文名称：** 临界区

**一句话定义：** 流程模型的两个或多个连通子图被标记为"临界区"。运行时，一个流程实例中**同一时刻只能有一个临界区在执行**——一个临界区开始后，必须执行完毕才能启动另一个。

**形式语义：** 互斥锁的语义——进入临界区获取锁，退出释放锁。

**编排类比：** Agent 编排中的互斥资源访问——两个 agent 不能同时修改同一份数据库记录。

**实例：** 两个子流程都要更新同一份库存记录——它们必须串行执行，不能交错。

---

### WCP40 — Interleaved Routing（交错路由）

**中文名称：** 交错路由

**一句话定义：** 集合中的每个任务必须**恰好执行一次**，顺序任意，但**同一时刻最多一个在执行**——无偏序约束。

**与 WCP17 的区别：** WCP17 有偏序约束（如 A 必须在 B 之前）；WCP40 完全无约束，纯粹任意顺序。

**实例：** 三个部门各自独立填写季度报告的对应部分——谁先谁后无所谓，但不能同时写（因为共享同一份模板文档）。

---

## 第6类：取消与强制完成（WCP19–20, 25–27）

这类模式处理"已经启动的事怎么优雅地停下来"——编排系统最难的部分之一。

---

### WCP19 — Cancel Activity（取消活动）

**中文名称：** 取消活动

**一句话定义：** 将一个**已使能但尚未完成**的活动实例撤回——不论它是在等待中还是已经在执行中。

**范围：** 单个活动实例。

**形式语义：** 收到取消信号时，如果该活动实例尚未开始，直接从待办列表中移除；如果正在执行中，通知执行者中止，回收任何已分配的资源，其产出 token 被丢弃。

**编排类比：** Agent 编排中的超时取消——一个 agent 超过 N 分钟没返回，取消它，走备用路径。

**实例：** 客户在支付审批中突然取消了订单——"审批支付"任务被撤回。

---

### WCP20 — Cancel Case（取消案例）

**中文名称：** 取消案例

**一句话定义：** 将**整个流程实例**终止——不论其中有多少活动正在运行、等待、或已完成。

**范围：** 整个流程实例。

**与 WCP19 的区别：** WCP19 取消一个活动但流程继续；WCP20 取消一切，流程死掉。

**编排类比：** 用户点了"取消生成"——所有正在跑的 agent 全部终止，整个编排实例标记为已取消。

**实例：** 投保流程进行到一半，保险公司发现投保人有欺诈记录——整案作废。

---

### WCP25 — Cancel Region（取消区域）

**中文名称：** 取消区域

**一句话定义：** 将流程中**一组活动**全部取消——范围大于单个活动（WCP19），但小于整个案例（WCP20）。

**形式语义：** 定义流程模型中的一个区域（节点集合）。当取消信号到达该区域的取消变迁时，区域内所有活跃/使能的活动实例被撤销，不产生任何 token。

**编排类比：** 编排中某个阶段失败后，把该阶段的所有 agent 都停了，但保留已完成的上一阶段的结果，从该阶段的入口重新开始。

**实例：** 一个订单处理流程的"信用审核"阶段——如果发现信息不足，把该阶段所有任务取消，退回"补充资料"，保留"订单录入"阶段的结果。

---

### WCP26 — Cancel Multiple Instance Activity（取消多实例活动）

**中文名称：** 取消多实例活动

**一句话定义：** 取消一个**多实例活动的所有实例**——不论它们已经完成、正在执行、还是等待中。

**与 WCP19 的区别：** WCP19 针对单个实例；WCP26 针对多实例活动的整个实例集合。

**实例：** 向 10 个供应商发出了询价，突然更换了采购标准——取消所有询价实例，按新标准重新发。

---

### WCP27 — Complete Multiple Instance Activity（完成多实例活动）

**中文名称：** 完成多实例活动

**一句话定义：** 强制将一个多实例活动标记为"已完成"——**所有尚在执行中或等待中的实例被终止**，而已完成的实例结果保留。

**与 WCP26 的区别：** WCP26 取消一切包括已完成实例的结果；WCP27 保留"已完成的"，强制结束"还在跑的"。

**编排类比：** "够了，就这些已经完成的 agent 返回的结果吧，不等了。"——超时强制截断。

**实例：** 询价发了 10 家，3 家已经回复了——等不及了，强制结束询价阶段，拿这 3 家的报价进入评估。

---

## 第7类：迭代模式（WCP10, 21–22）

迭代模式处理"走回头路"——重复执行已经执行过的活动。

---

### WCP10 — Arbitrary Cycles（任意循环）

**中文名称：** 任意循环

**一句话定义：** 流程模型中的活动或子流程支持**非结构化的、无约束的循环/回退**——不要求循环有明确的入口/出口结构。

**形式语义：** 与结构化循环不同，任意循环允许以任何方式回到任何已经执行过的点——不存在一个统一的"循环起点"和"循环终点"。

**编排类比：** Agent 在执行中出错后，不是从固定的节点开始重试，而是可能退回到上游的任意一步——取决于错误的类型。

**评估：** 许多 BPM 系统（尤其是 BPEL）**不支持**任意循环，因为它让流程分析（可达性、死锁检测）变得极端复杂。它们只支持结构化循环（WCP21）。

---

### WCP21 — Structured Loop（结构化循环）

**中文名称：** 结构化循环

**一句话定义：** 一个活动或子流程的重复执行的次数由一个前置条件或后置条件**明确界定**——while-do 或 repeat-until 结构。

**形式语义：**
- **while-do：** 每次执行前检查条件，条件为真则执行
- **repeat-until：** 先执行一次，然后检查条件，条件为假则重复

**与 WCP10 的区别：** 结构化循环有明确入口/出口；任意循环没有。

**编排类比：** Agent 的重试循环——`while attempts < max_retries and not success`。LangGraph 的自环（self-loop edge）。

**实例：** 付款失败后重试，直到成功或达到最大重试次数。

---

### WCP22 — Recursion（递归）

**中文名称：** 递归

**一句话定义：** 一个活动在执行过程中，**作为自身的一个子活动**被再次调用——调用栈更深了一层，而非简单的循环。

**与 WCP21 的区别：** 循环是平层的重复；递归是嵌套的——内层调用有自己独立的上下文。

**编排类比：** Agent 在处理一个任务时，发现自己需要先处理一个同类但更小的子任务——递归调用自己。

**实例：** 审批「部门预算」时，发现某子项目预算也超标了——发起一个嵌套的「审批子项目预算」。

**注意：** 大多数工作流引擎**不支持递归**，因为它的执行语义比循环复杂得多。

---

## 第8类：终止模式（WCP11, 43）

---

### WCP11 — Implicit Termination（隐式终止）

**中文名称：** 隐式终止

**一句话定义：** 一个流程（或子流程）实例在**没有任何事可以做的时候**自动终止——不存在死锁、不存在待处理的 token。

**形式语义：** 当流程的 Petri 网中没有任何变迁被使能，且不处于死锁状态时，实例自动结束。

**编排类比：** 所有 agent 都跑完了，所有 token 都消费了，图自然静止——不需要显式说"结束"。

---

### WCP43 — Explicit Termination（显式终止）

**中文名称：** 显式终止

**一句话定义：** 一个流程（或子流程）实例在**到达一个指定的终止节点时**强制终止——无论是否有活动仍在执行中，一律取消。

**与 WCP11 的区别：** 隐式终止是"自然死亡"；显式终止是"强制枪毙"。

**编排类比：** 用户在中途点了"停止生成"——不管是否还有 agent 在跑，全部 kill。

**风险：** 在并发场景中，显式终止可能导致流程处于不一致状态——正在执行的活动被突然中断。

---

## 第9类：触发模式（WCP23–24）

触发模式描述"外部信号如何启动流程中的活动"。

---

### WCP23 — Transient Trigger（瞬时触发）

**中文名称：** 瞬时触发

**一句话定义：** 一个活动可以被一个**外部信号触发**，但该信号是**瞬时的**——如果信号到达时活动尚未被使能（前置条件不满足），信号就永久丢失。

**形式语义：** 触发信号不排队、不缓存、不重发。要么当场消费，要么永远错过。

**编排类比：** "3 秒内如果没有收到回调就超时"——时间窗口类信号。

**实例：** "订单取消"信号可以在客户确认之前任何时候到达——但如果订单已经进入"已发货"状态，取消信号就无效了。

---

### WCP24 — Persistent Trigger（持久触发）

**中文名称：** 持久触发

**一句话定义：** 一个活动可以被一个外部信号触发，信号是持久的——**如果信号到达时活动尚未被使能，信号会一直等待，直到活动变为可用**。

**形式语义：** 触发信号被缓存/排队。活动被使能后，检查是否有等待中的信号，若有则消费。

**与 WCP23 的区别：** 瞬时触发是"要么现在要么永不"；持久触发是"我先存着，等你准备好了用"。

**编排类比：** 消息队列——Kafka/NATS 中持久化的信令。

**实例：** "VIP 客户升级"信号在客户还在走普通流程时到达——存着，等普通流程走完后触发升级逻辑。

---

## 模式与编排引擎的对照关系

### 与 LangGraph 的对应

| Workflow Pattern | LangGraph 对应 |
|------------------|---------------|
| WCP1 Sequence | `add_edge("A", "B")` |
| WCP2 Parallel Split | `Send` API — 向多个目标节点发消息 |
| WCP3 Synchronization | `add_edge(["B", "C"], "D")` — 等 B 和 C 都完成 |
| WCP4 Exclusive Choice | `add_conditional_edges` — 条件路由 |
| WCP5 Simple Merge | 多个节点指向同一节点（默认语义） |
| WCP10/WCP21 Loop | self-loop edge（自环） |
| WCP16 Deferred Choice | `interrupt()` + `Command(resume=...)` |
| WCP19 Cancel Activity | `interrupt()` — 暂停等待 |
| WCP20 Cancel Case | 抛出异常终止整个 graph run |

### 与 Temporal 的对应

| Workflow Pattern | Temporal 对应 |
|------------------|--------------|
| WCP1 Sequence | 代码本身的顺序执行 |
| WCP2 Parallel Split | `Promise.all([activity1(), activity2()])` |
| WCP3 Synchronization | `Promise.all` 的返回 |
| WCP4 Exclusive Choice | `if/else` 分支 |
| WCP9 Discriminator | `Promise.race([a, b, c])` |
| WCP15 Dynamic MI | `for await` 配合动态条件 |
| WCP19 Cancel Activity | `CancellationToken` / `ActivityHeartbeat` timeout |
| WCP21 Structured Loop | `while (await condition()) { ... }` |
| WCP24 Persistent Trigger | Signal（信号等待） |

### 与 Dify / Coze 工作流模式的对应

| Workflow Pattern | Dify / Coze 对应 |
|------------------|-----------------|
| WCP1 Sequence | 节点连线 |
| WCP2 Parallel Split | 从一个节点连出多条线 |
| WCP4 Exclusive Choice | 条件分支节点 |
| WCP6 Multi-Choice | 多个条件分支管线可能同时激活（部分支持） |
| WCP12 MI without Sync | 循环 + 异步无等待 |
| WCP16 Deferred Choice | 用户输入等待节点 |
