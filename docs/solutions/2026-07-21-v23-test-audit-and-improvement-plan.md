## 三、综合诊断

### 3.1 优势

| 优势 | 证据 | 可信度 |
|------|------|--------|
| **输出稳定性极高** | 盲测 50 std=0.038, GLM n=30 std=0.122（三者最低） | 高 |
| **零严重失误** | 盲测 50 VETO=0, GLM n=30 VETO=0 | 高 |
| **对话忠实度完美** | 盲测 50 dialogue_fidelity=5.0, 人话感=5.0 | 中（self-eval bias） |
| **触发准确率满分** | 基线报告 M1=1.0（5/5） | 低（n=5） |
| **Golden Bank 结构化评分体系完善** | 6-dim custom rubric，逐案对照专家标注 | 高 |

### 3.2 劣势

| 劣势 | 证据 | 可信度 | 严重度 |
|------|------|--------|--------|
| **Tone 匹配是系统性短板** | M5=0.400 (基线), 0.444 (感知层) | 高 | 🔴 致命 |
| **新场景泛化不足** | 12 新用例 0.625 vs 70 校标 0.883（差 0.258） | 高 | 🔴 致命 |
| **Judge 不可靠** | Pearson r=0.021, 最大偏差 ±0.476 | 高 | 🟡 影响所有分数 |
| **看见感偏弱** | 盲测 50 being_seen=4.66（五维最低） | 中 | 🟡 可改善 |
| **洞察深度中等** | M6=3.8/5 (基线), 3.056/5 (感知层) | 中 | 🟡 可改善 |
| **保守策略** | 三方盲评 win 数第二但均分第一——"不输但不赢" | 中 | 🟢 风格特征 |

### 3.3 根因分析

```
v2.3 的三个根因问题：

1. Tone 盲区（M5=0.400）
   根因：v2.3 的 tone 分类逻辑写在 system_prompt 的自然语言中，
   而非确定性规则引擎。LLM 在 short-popup 场景下倾向输出
   diagnostic（因为"指出问题"比"庆祝做对"更容易生成），
   导致 empowering tone 案例被系统性误判为 diagnostic。

2. 泛化断裂（新用例 0.625）
   根因：v2.3 是三位专家在固定 70 题上手工打磨的产物。
   专家标注覆盖的对话模式有限——当新对话出现未见的互动模式
   （如"摆碗碎碗 C5-001""收盘子 DS_001"），v2.3 的策略库
   缺少对应模板，弹出内容质量断崖式下降。

3. Judge 噪声（Pearson r=0.021）
   根因：deepseek-chat 做 judge 时缺少领域专业知识（亲子沟通
   心理学），其评分与人类专家的共识度不比随机高多少。
   这意味着 TEST 8/10/12 的所有评分都有 ±0.2 的不确定性。
```

## 四、调整改善方案

### 4.1 短期（1-2 天，低风险）

#### R1 · 引入 Claude 裁判替换 DeepSeek Judge 🔴 优先级最高

**问题**：deepseek-chat judge 与人类专家 Pearson r=0.021，所有分数不可信。
**方案**：
- 将 judge model 从 `deepseek-chat` 切换为 `claude-opus-4-8`（已有 endpoint：`api.xingluan.vip`，key 已在 `.env`）
- 修改 `optimizer.py` 和 `baseline_runner.py` 的 judge 调用逻辑，走 xingluan Claude
- 重跑 TEST 8（盲测 50）和 TEST 10（生产交接对比）用 Claude judge，获取可信基线

**预期效果**：建立可信的评测基准，所有后续分数不再含 ±0.2 噪声。
**风险**：低（仅改 judge 调用路径，不碰 prompt 和生产逻辑）。
**工作量**：~2h。

---

#### R2 · v2.3 Tone 专项诊断与修复 🟡

**问题**：M5=0.400，近 60% 案例 tone 判错。
**方案**：
1. 从 70 全量 case 中挑出 v2.3 tone 判错的案例（预计 28-30 个）
2. 逐案分析：是 prompt 中的 tone 选择规则模糊，还是 LLM 倾向性偏差？
3. 在 system_prompt 的 tone 判定段增加 3-5 个反例（"以下情况必须选 empowering，即使看起来像 diagnostic：..."）
4. 用 Claude judge 重测 M5，目标 >0.70

**预期效果**：M5 从 0.400 提升到 0.65-0.75。
**风险**：低-中（修改 system_prompt 可能引入新退化，需盲测验证）。
**工作量**：~4h。

---

#### R3 · 新场景泛化强化 🟡

**问题**：12 新用例 0.625，与 70 校标 0.883 差距 0.258。
**方案**：
1. 分析 12 新用例中低分 case（C5-001 摆碗碎碗 0.463, DS_001 收盘子 0.513）的失败模式
2. 在 v2.3 prompt 的策略库中补充"边缘场景处理"段——当遇到不匹配任何模板的对话时，走安全兜底策略
3. 用另外 10 个未见过的新 case 做 holdout 验证

**预期效果**：新用例均分从 0.625 提升到 >0.78。
**风险**：中（改变 v2.3 策略库可能影响已稳定的 70 case 表现）。
**工作量**：~6h。

---

### 4.2 中期（1-2 周，需设计评审）

#### R4 · Judge 标定体系重构 🔴

**当前状态**：单 judge 一次打分，噪声 ±0.2。
**目标状态**：多 judge 交叉验证，置信区间 ±0.05。

**方案**：
1. **双 judge 交叉验证**：每个弹窗同时由 Claude + 人类专家（晓浩/廖老师）打分，计算 IRR（评分者间信度）
2. **Rubric 重写**：将当前 5-dim rubric 改写为行为锚定评分量表（BARS），每个分数点配一个标准示例
3. **锚定样本集**：选 10 个"高分标准弹窗"和 10 个"低分标准弹窗"作为 judge 的前置校准
4. **Triangulation**：关键决策（如生产上线）使用 3 judge × 3 run 的 9 分取中位数

**预期效果**：Judge 评分者间信度 >0.8, judge-专家相关性 >0.6。
**风险**：低（仅改进评测体系，不影响生产）。
**工作量**：~3 天。

---

#### R5 · Holding Set 标准化 🟡

**当前状态**：70 全量校标被反复用于迭代和评测 → **数据泄露**。
**目标状态**：锁定 holdout set，禁止用于迭代。

**方案**：
1. 从 70 全量 case 中随机抽 15 个作为 **永久 holdout**（仅用于最终评测，绝不用于 DSPy 训练或 prompt 手动调优）
2. 剩余 55 个作为 train/val pool
3. 在 `config_v4.yaml` 中硬编码 holdout case_id 列表
4. CI 检查：任何评测脚本读入 holdout 案例即报警

**预期效果**：消除数据泄露导致的分数虚高（估计虚高 +0.03-0.05）。
**风险**：低。
**工作量**：~2h。

---

#### R6 · v2.3 感知层废弃或重构 🟢

**当前状态**：`prompt_感知层_v2.3.md` 在独立运作时 overall=0.667, M5=0.444。
**建议**：废弃该文件——它是在多智能体架构早期写的，现已不适用。

**替代方案（如果确实需要感知层）**：
- 用 v4.0.12 的输出（包含结构化的洞察+矛盾+tone）作为感知层的等价替代
- 或者用已有的 `prompt_感知层_v3.1.md`（星灵多智能体统一版本）

**风险**：低（v2.3 感知层不在任何生产路径上）。
**工作量**：~1h（标记废弃 + 清理引用）。

---

### 4.3 长期（1 月+，需团队讨论）

#### R7 · 路线 A vs 路线 B 最终定位决策

**当前困局**：
- 路线 A（单智能体）：v4.0.12 生产运行，v2.3 回退保留，v1.7 待验证
- 路线 B（多智能体）：v3.1 迭代停滞（规则引擎硬编码 tone 限制 prompt 进化）

**需要决策的问题**：
1. v1.7 是否继续投入做 n≥27 对比？还是接受现有证据（v4.0.12 大概率优于 v1.7）直接淘汰？
2. 路线 B 的规则引擎 `tone_rules.py` 是否需要重构为 LLM-based（解除硬编码限制）？
3. 最终目标是"单智能体一家独大"还是"两条路线互补"？

**建议**：下次团队会议列入议程。当前先聚焦 R1-R5。
